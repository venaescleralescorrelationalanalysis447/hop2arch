## 1. Что это за проект

**hop2arch** — инструмент, который переносит человека с Windows на Arch Linux.
Не «установщик» и не «дистрибутив», а мост: он инвентаризирует машину, с которой
уходят, честно объясняет что именно потеряется, и собирает машину, на которую
приходят.

CLI называется `hop`. Одна команда делает переезд целиком, три — по шагам:

```
hop go       # на Windows: весь переезд — скан, план, флешка, перезагрузка
hop install  # внутри Arch ISO: выбор диска, разметка, установка

hop scan     # на Windows: windows/hop-scan.ps1 -> hopfile.json + hop-payload/
hop plan     # где угодно:  hopfile.json -> hop-plan.json + hop-report.md
hop land     # на Arch:     выполняет план — пакеты, payload, настройки
```

Вспомогательные: `hop install-config` (генерит конфиг archinstall), `hop diff`
(что ещё не доехало), `hop doctor` (проверки), `hop scrub` (анонимизация hopfile
для публикации в issue), `hop db` (lint/stats/search по базе маппинга).

Путь «одной команды» появился позже остального и описан в §2b — там же разобраны
два решения, которые легко сломать, не поняв: почему носитель собирается файлами,
а не сырым дампом, и почему разметка считается на стороне Arch.

### Ключевая идея, ради которой это вообще существует

Главная ценность — не код, а `hop/data/packages.toml`: база соответствий
«программа Windows → пакет Arch» с **честными** формулировками. Adobe не
подменяется бодрым «просто используй GIMP» — там написано что реально теряется.
Это и есть точка входа для контрибьюторов: правка одной записи = PR из двух строк.

### Тон

Читатель нервничает: он собирается стереть ОС, которой пользовался 15 лет.
Отчёт идёт от худших новостей к лучшим (blockers → web → wine → аналоги →
нативное → уже в системе). Никакого евангелизма, никаких «лол ставь линукс».
Поле `notes` в базе — одно-два предложения, спокойно, по делу.

## 2b. Путь «одной команды» (`hop go`)

Появился после того, как владелец сформулировал цель прямо: «одной командой с винды
на арч». Разбор упирается в физику — нельзя разметить диск, с которого сейчас
загружен, — поэтому перезагрузка неустранима. Всё остальное вокруг неё убрано:

```
hop go            Windows: скан → план → отчёт → ОДНО подтверждение
                  → скачать и проверить ISO → собрать флешку с планом и payload
                  → одноразовая загрузочная запись → reboot
hop install       внутри Arch ISO, запускается сама: живой lsblk → показать диск
                  → набрать его путь руками → archinstall → hop land после первой загрузки
```

### Два решения, которые стоит понимать, прежде чем их менять

**Носитель — FAT32 с файлами, а не сырой дамп ISO.** Обычно ISO пишут через
`dd`/raw-запись в `\\.\PhysicalDrive`, и промах в номере устройства стирает не ту
железку. Вместо этого используется документированный на Arch Wiki способ:
отформатировать съёмный носитель в FAT32 с меткой ISO и скопировать содержимое
образа обычными файловыми вызовами. UEFI грузится с такого носителя штатно,
raw-доступ не нужен вовсе, и на той же ФС остаётся место для hopfile, плана и
payload. Плата: **legacy BIOS так не грузится**, и `hop go` отказывается на первой
же стадии, а не через три минуты после начала скачивания.

**Разметка считается на стороне Arch по живому `lsblk`, а не по hopfile.** Это
разворот решения, которое §4 отстаивало для `hop/archinstall.py`: тот по-прежнему
принципиально не пишет `disk_config`, и правильно делает. Возражение было про
устаревший снимок — план описывает машину, какой она была дни назад, за это время
можно добавить диск, и `/dev/nvme0n1` будет означать другое. Возражение снимается
не отказом от автоматизации, а переносом решения туда, где данные свежие.
`hop/install.py` — единственный компонент, которому разрешено выдать `disk_config`,
и он не читает hopfile, чтобы решить, что стирать.

**Подтверждение — ввод пути устройства, а не «yes».** Чтобы набрать `/dev/nvme0n1`,
надо прочитать строку выше с моделью, размером и списком разделов. Чтобы набрать
«yes», читать не надо ничего. По той же причине `usb.prepare()` принимает не
булев флаг, а идентификатор диска: флаг можно протащить через три вызова и потерять
по дороге смысл, идентичность потерять нельзя.

## 4. Архитектурные решения, которые уже приняты

### hopfile.json (docs/HOPFILE.md)

Единый JSON, версия 1. Всё кроме `hopfile_version` / `generated_at` /
`generator` опционально: сканер работает без админских прав и деградирует в
`null`, никогда не падает. Рядом — `hop-payload/` с реальными байтами того, что
стоит увезти (SSH-ключи, Wi-Fi, закладки, обои, шрифты, конфиги терминала);
JSON ссылается на них относительными путями через `payload.entries`.

Приватные ключи **никогда** не попадают в JSON — только в payload и только с
флагом `-WithSecrets`.

### packages.toml (docs/MAPPING.md)

Плоские `[[app]]` записи. Семь стратегий:

| strategy | смысл |
|---|---|
| `native` | то же приложение есть в Arch |
| `alternative` | другое приложение делает ту же работу (обязателен `replacement`) |
| `builtin` | уже покрыто базой/DE, ставить нечего |
| `compat` | оставляем виндовый бинарник, крутим через Wine/Proton |
| `web` | десктопного клиента нет, живём в браузере |
| `none` | пути нет — это blocker, пользователь должен решить сам |
| `ignore` | не приложение (редисты, драйверы, апдейтеры) |

Приоритет источников: `pacman` > `aur` > `flatpak` (переворачивается флагом
`--prefer-flatpak`).

### Матчер (hop/mapping.py)

Четыре прохода, от самого уверенного к самому дешёвому: точный `winget` id →
`exe` → подстрока в имени (**длинные подстроки первыми**, чтобы
«visual studio code» выигрывал у «visual studio») → регекс. Каждый результат
несёт `method` и `matched_on`, чтобы отчёт мог показать почему так решил.

### Скоринг (hop/plan.py, `_score`)

«Hoppability» — взвешенное покрытие. Веса в `STRATEGY_WEIGHT`:
native/builtin = 1.0, alternative = 0.75, compat = 0.5, web = 0.4, none = 0.0.
`ignore` не считается вообще. **Unknown считается как ноль** — сознательно:
неспособность ответить это реальная цена для пользователя, прятать её значит
врать числом.

### Системные пакеты

Планировщик добавляет пакеты, которые следуют из железа и локали, а не из списка
программ: драйверы GPU по нормализованному вендору, DE (по умолчанию Plasma —
ближе всего к Windows), PipeWire, шрифты (+CJK если локаль того требует),
ноутбучный набор (tlp/bluez/brightnessctl), игровой стек если найден Steam,
`ntfs-3g` всегда. Каждый пакет попадает в `plan.package_reasons` с объяснением —
отчёт показывает не только «что», но и «почему».

### Раскладки и локаль

`KLID_TO_XKB` в `hop/plan.py` — таблица виндовых id раскладок → xkb.
`_to_posix_locale('ru-RU')` → `ru_RU.UTF-8`.

   прогон, потом `hop plan` на получившемся hopfile.

   виртуалке, со снапшотом до. Проверять по фазам: `--only packages`, потом
   `--only payload`, потом `--only settings`.

4. **Прогнать `hop go` на настоящей флешке.** Начать с `--no-reboot`: он
   останавливается, когда носитель готов, и не трогает загрузочную запись. Смотреть
   на список кандидатов — он должен показать флешку и не показать ничего другого.

## 6. Известные проблемы

Старый список закрыт целиком: скрипт парсится реальным парсером в CI,
`Database.lint()` ослаблен, `bytes_label` убран, размеры пользовательских папок
выводятся в секции «Data worth carrying». Ниже — то, что открыто сейчас.

**Не проверено на живом железе (главное).**

- `windows/hop-scan.ps1` ни разу не читал настоящий реестр. Парсинг, PSScriptAnalyzer
  и юнит-тесты чистых хелперов — не замена запуску. Самое вероятное место поломки:
  ветки, зависящие от прав, и `ConvertTo-Json` на одноэлементных массивах.
- `hop land --execute` ни разу не выполнялся на Arch. Dry run вычитан построчно и
  покрыт тестами, реальный путь — нет.
- **`hop go` и `hop install` не видели железа вообще.** Они покрыты тестами через
  подставные seams — консервированный вывод `Get-Disk` и `lsblk`, фальшивый
  загрузчик, фальшивый форматтер — и отдельно проверены состязательным аудитом на
  то, как именно могли бы уничтожить не то. Аудит нашёл 12 дефектов, среди них два
  показательных: `New-Partition -Size` получал размер **всего диска**, из-за чего
  любая флешка меньше 32 ГБ стиралась и потом не форматировалась; и образ, чью
  подпись gpg **отверг**, предлагался обычным вопросом «продолжить? yes» — тем же
  словом, что и безобидный случай «gpg не установлен». Оба исправлены. Ни то, ни
  другое не заменяет одного настоящего запуска.
- Автозапуск `hop install` в live-среде висит на параметре ядра `script=` archiso.
  Никто здесь не подтверждал, что он срабатывает. Если нет — флешка всё равно
  грузится, а bootstrap-скрипт печатает команду для ручного запуска.
- Одноразовая загрузочная запись через `bcdedit /set {fwbootmgr} bootsequence` —
  best-effort. Не сработает — hop печатает, какой клавишей открыть меню загрузки.
- CI ни разу не запускался: репозитория не существует.

**Осознанно оставлено как есть.**

- Скоринг по-прежнему не учитывает игры. Смешивать «сколько программ доедет» и
  «сколько игр запустится» в одно число — значит сделать оба хуже; игры уже
  отдельной секцией и отдельной строкой в summary.
- `PlanItem.packages` — это всё меню, которое правило предлагает для источника, а
  `.package` — то, что hop реально ставит. Поэтому `.packages` законно называет
  пакеты, которых нет в плане (`p7zip` у 7-Zip, `gimp` у Photoshop). Инвариант,
  который держит нагрузку, другой, и он теперь под тестом: каждый `item.package`
  присутствует в `plan.packages[item.install_source]`.
- `_collect_packages` выбрасывает AUR-пакет, если он же есть в pacman-корзине, но
  оставляет `install_source` = `aur` у item. Проверены все правила базы против
  всех систем, GPU, DE и игровых наборов: сегодня до этой ветки не добраться.
  Поведение зафиксировано тестом, разрешение конфликта не трогалось.

**Мелочи.**

- `docs/` не описывает `hop go`: формат hopfile и формат базы актуальны, а путь
  «одной команды» задокументирован только в README и здесь.
- `docs/MAPPING.md` описывает четыре прохода матчера, README — те же четыре плюс
  пятый шаг «ничего не нашлось». Если формат матчера будет меняться, править оба.
